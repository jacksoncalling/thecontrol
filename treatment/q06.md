## Prompt (pasted exactly, from prompts/q06.txt)

```
Context: The Larder team (invented meal-planning app) wants to build "shopping list sorted by supermarket aisle". They listed four assumptions with what they currently know:

A1 (desirability): Shoppers want their list sorted by aisle. Evidence: in 9 of the last 12 customer interviews, participants told specific recent stories of walking back and forth in the store because of list order. If this were false, the idea would fail.
A2 (feasibility): We can get accurate aisle layouts for the store each user actually shops at. Evidence: none; nobody on the team knows of a source for this data. If this were false, the idea would fail.
A3 (usability): Users will notice the "sort by aisle" toggle. Evidence: none. If this were false, we could simply make aisle sorting the default, so the idea would still work.
A4 (viability): Storing aisle data will cost less than 200 euros per month. Evidence: engineering priced it at about 40 euros per month using current hosting. If this were false, the idea would be somewhat less attractive but could still go ahead.

Using Teresa Torres' approach to assumption testing, which ONE assumption should the team test first, and why? Name the reasoning tool she uses to decide.
```

## Response (raw, copied with the copy button, not edited)

Test **A2 (feasibility): getting accurate aisle layouts for the store each user actually shops at.**

**The reasoning tool: the assumption map.** Torres plots every assumption on a 2x2 grid:

- **Importance:** if this assumption is false, does the solution fail? Assumptions that would only dent the idea, or could be designed around, are low importance.
- **Evidence:** how much do we already know about whether it's true? This is the "how confident are we" axis from the experiments workspace.

She tests first the assumptions in the quadrant that is **high importance and little or no evidence** (the "leap of faith" assumptions). Everything else can wait.

**Placing the four assumptions:**

|Assumption|Importance (fails → idea fails?)|Evidence|Quadrant|
|---|---|---|---|
|A1 Desirability|High|Strong: 9 of 12 interviews with specific, recent stories|High importance, strong evidence: already covered, don't test|
|A2 Feasibility|High|None|**High importance, no evidence: test first**|
|A3 Usability|Low: default sorting is a workaround|None|Low importance: no test needed, just design around it|
|A4 Viability|Low-ish: idea survives a miss|Decent: priced at ~€40 vs. a €200 ceiling|Low importance, reasonable evidence: park|

**Why A2 and not the others:**

- A1 looks like the obvious candidate because desirability is usually tested first, but the team has already done that work through story-based interviews, which is the high-fidelity kind of evidence. Retesting it would be learning nothing new.
- A3 has no evidence either, but a failure doesn't kill the idea (make the sort the default), so it isn't worth a test.
- A4 would only make the idea "somewhat less attractive," and a €40 estimate against a €200 limit leaves wide margin.
- A2 is the only one where a "no" ends the idea and the team has no information at all. Nobody knows a data source. If it fails, building anything else is wasted effort.

**Suggested shape of the test (hours, not weeks):** pick the three or four supermarket chains your users actually shop at, and check whether any source (chain APIs, open data, licensed providers, crowdsourcing) gives store-level aisle layouts. Set the pass/fail line in advance, for example "layouts available for chains covering at least X% of our users' stores." If it fails, return to the solution set and consider alternatives that don't need layout data, such as sorting by generic category (produce, dairy, frozen) or letting users learn their own store's order.
